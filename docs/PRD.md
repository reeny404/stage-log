- 포트폴리오 대상: Mnet Plus Frontend Engineer

## 1. 제품 정의

> 모든 팬이 한꺼번에 도착하는 순간에도 이벤트 정보를 잃지 않고, 안전하게 입장하고, 참여를 이어가는 경험.

StageLog는 라이브 영상을 제공하는 스트리밍 플랫폼이 아니다. 시상식·콘서트 이벤트 오픈 순간에 발생하는 세 문제를 다룬다.

1. 공개 일정 조회와 개인 입장 쓰기가 동시에 급증한다.
2. 사용자가 응답을 기다리며 버튼을 반복해서 눌러 중복 요청을 만든다.
3. 투표·랭킹 등 일부 기능의 장애가 전체 이벤트 장애처럼 느껴진다.

공개 이벤트 셸, 보호된 입장, 선택적 실시간 기능을 분리해 각 기능이 독립적으로 부하와 장애에 대응하도록 만든다.

## 2. 정직성 원칙

개인 프로젝트에 실제 대규모 사용자가 없다는 사실을 숨기지 않는다.

- 정상·피크·장애 상태는 UI와 네트워크 계약을 위한 simulation이다.
- k6 결과는 지정한 테스트 환경에서 생성한 가상 부하 결과로만 표현한다.
- 테스트 수치는 실행 환경, commit, 날짜, 원본 요약과 함께 기록한다.
- 실제 동시 접속자 또는 프로덕션 트래픽을 처리했다고 주장하지 않는다.
- 실제 분산 대기열에 필요한 영속 저장, 봇 방어, 토큰 서명은 후속 요구사항으로 구분한다.

## 4. 핵심 사용자 여정

```text
캐시 가능한 이벤트 셸 진입
  → 현지 시각과 참여 규칙 확인
  → idempotency key와 함께 입장 요청
  → 정상: 즉시 입장
  → 피크: 대기 토큰 수신 → 상태만 조회 → 입장
  → 장애: 이벤트 셸 유지 → 요청 키를 보존한 안전한 재시도
  → 입장 후 투표·클립·미션이 독립적으로 공개
```

## 5. MVP 범위

### P0. 이벤트 셸

- 이벤트 제목, 일정, 지역, 드롭 순서를 Server Component에서 렌더링한다.
- 개인화 데이터와 브라우저 API를 포함하지 않는다.
- 현지 시각 변환만 작은 Client Component로 격리한다.
- 공유 링크와 새로고침에서 동일한 공개 정보가 표시된다.

### P0. 입장 Traffic Lab

- `Normal`: 즉시 pass를 받는다.
- `Peak surge`: 최초 요청 후 대기 상태만 주기적으로 조회한다.
- `Failure drill`: 503과 재시도 가능 상태를 사용자에게 설명한다.
- 세 시나리오는 리뷰어가 UI에서 직접 전환할 수 있다.
- simulation이라는 사실을 화면에 명시한다.

### P0. 요청 안전성

- 최초 입장 요청마다 idempotency key를 생성한다.
- 동일한 시나리오의 재시도에는 같은 키를 유지한다.
- 대기 상태 갱신은 최초 입장 요청을 다시 보내지 않는다.
- 네트워크 오류 시 사용자가 요청 결과를 오해하지 않도록 상태를 보여준다.

### P0. 검증

- 입장 상태 전이를 순수 함수 단위 테스트로 검증한다.
- “홈 → 이벤트 → 대기 → 입장”을 Playwright로 검증한다.
- k6에서 공개 읽기와 개인 쓰기를 별도 시나리오·태그로 실행한다.
- lint, unit test, build, E2E를 CI에서 실행한다.

### P1. Timed Drop

- 투표, 클립, 미션을 독립 기능 경계로 구현한다.
- 투표는 서버 확정 전까지 `제출 중`과 `완료`를 구분한다.
- 중복 투표는 idempotency key 또는 사용자·이벤트 유일 키로 막는다.
- 랭킹 실패 시 투표 결과와 이벤트 정보에는 영향을 주지 않는다.

### P1. 운영 모드

- 기능별 상태: `normal`, `read-only`, `paused`.
- 운영자가 투표·랭킹·반응을 독립적으로 제한한다.
- 변경자, 시각, 사유를 운영 로그에 남긴다.
- 위험한 변경은 확인과 롤백 경로를 제공한다.

## 6. 비기능 요구사항

### 성능

- 모바일 LCP 2.5초 이하를 목표로 하되 실측 전에는 결과로 표기하지 않는다.
- 이벤트 셸 초기 JavaScript를 지속 추적한다.
- 입장 Client Component가 페이지 전체를 client rendering으로 바꾸지 않아야 한다.

### 회복력

- admission 장애가 이벤트 셸을 가리지 않는다.
- polling 실패 시 마지막 정상 상태를 유지한다.
- 투표·랭킹·반응의 장애는 기능별로 격리한다.
- 모든 쓰기는 `pending`, `confirmed`, `unknown`, `failed`를 구분한다.

### 접근성·글로벌

- 키보드만으로 시나리오 선택과 입장 요청을 완료할 수 있다.
- 대기·장애 상태를 색상만으로 표현하지 않는다.
- 상태 변경은 `aria-live`로 전달한다.
- locale과 timezone을 별도 개념으로 관리한다.
- `prefers-reduced-motion`에서 장식 애니메이션을 줄인다.

## 7. 아키텍처 경계

| 영역 | 렌더링/요청 | 캐시 | 실패 전략 |
| --- | --- | --- | --- |
| 이벤트 셸 | Server Component, 정적 생성 | CDN 대상 | 마지막 공개 정보를 계속 제공 |
| 현지 시각 | Client Component | 해당 없음 | ISO 원본 시각을 함께 유지 |
| 입장 요청 | POST Route Handler | `no-store` | 대기열 또는 안전한 재시도 |
| 대기 상태 | GET polling | `no-store` | 마지막 위치 유지 |
| timed drop 자산 | 독립 공개 읽기 | CDN 대상 | 개인화 없이도 콘텐츠 표시 |
| 투표·랭킹 | 독립 동적 기능 | 기능별 | read-only 또는 일시 중단 |

실제 서비스에서는 대기열·idempotency 저장소를 Next.js 프로세스 메모리에 두지 않는다. 현재 demo route는 UI 계약만 재현하며, 외부 durable queue adapter로 교체할 경계를 남긴다.

## 8. 상태 모델

```text
idle → checking → admitted
                 └→ queued → admitted
                 └→ degraded → checking
```

- `checking`: 최초 쓰기의 결과를 기다리는 상태
- `queued`: 입장 요청은 접수됐고 상태 조회만 허용되는 상태
- `admitted`: pass가 확정된 상태
- `degraded`: 성공 여부를 추측하지 않고 안전한 복구 경로를 제공하는 상태

## 9. 측정 계획

| 범주 | 지표 | 검증 목적 |
| --- | --- | --- |
| UX | LCP, CLS, INP | 이벤트 셸의 초기 경험 |
| 입장 | 요청 성공·대기·degraded 비율 | 각 경로가 구분되는지 확인 |
| 중복 | 요청 키당 admission POST 수 | polling이 재입장을 만들지 않는지 확인 |
| 부하 | 읽기/쓰기별 p95와 실패율 | 캐시 가능한 경로와 동적 경로 비교 |
| 복구 | 장애 후 성공까지 걸린 시간 | 재시도 UX와 운영 전략 평가 |

## 10. 제외 범위

- 실제 영상 스트리밍, DRM, 미디어 CDN

- 프로덕션용 분산 대기열과 봇 방어
- 결제, 티켓 구매, 좌석 배정
